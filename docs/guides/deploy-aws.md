# Deploy to AWS

PIIShield's Terraform is complete and validated for three environments, but per this
program's standing rule, nothing is ever applied to a real AWS account by the project
itself: `aws-dev` and `aws-prod` are validated, linted and security-scanned, and exercised
end to end against a throwaway Floci emulator (`make tf-aws-on-floci`), so the IaC is
proven deployable without ever touching a real account in this repository's own
verification. Deploying for real is something you choose to do with your own AWS account
and credentials.

## Environments

| Env | Purpose |
| --- | --- |
| `local-floci` | Applied automatically by `make up`, against the local Floci emulator. Not a deployment target, it is how the local stack proves its own Terraform. |
| `aws-dev` | A full, cheaper copy of production: 2 AZs, a single NAT gateway, single-AZ database, one cache node, no deletion protection, small autoscaling ceilings. |
| `aws-prod` | Multi-AZ, deletion protection on, larger ceilings. |

Modules (`infra/terraform/modules/`): `network`, `database` (RDS PostgreSQL), `cache`
(ElastiCache), `storage` (S3), `kms`, `secrets` (Secrets Manager), `ecr`, `service` (ECS
Fargate behind an ALB), `observability` (CloudWatch), `email` (SES).

## Key mode in this release

Both `aws-dev/main.tf` and `aws-prod/main.tf` set `KEY_MODE = "local"` in the ECS task
environment, matching the only key backend 0.1.0's application code implements
(`core/sealing.py build_sealer` raises `NotImplementedError` immediately for
`key_mode=kms`, by design, rather than silently falling back to a weaker key backend; see
[ADR-0001](../architecture/adr/0001-envelope-encryption-local-key-only.md)). The real
`LOCAL_MASTER_KEY` that seals the vault is generated by `module.secrets` and injected
through Secrets Manager, the same way as `SESSION_SECRET` and `API_KEY_PEPPER`. Both
environments still provision a real KMS key and alias (`module.kms`): it exists for a
future KMS-backed `Sealer` behind the same `Protocol`, and is what `make tf-aws-on-floci`
exercises; nothing in 0.1.0's running application reads it yet. Do not set `KEY_MODE=kms`
against this release's application image: it will refuse to boot.

## Prerequisites to deploy for real

- An AWS account and credentials with permission to create the resources above.
- A domain you control, if you want SES to send mail and Route 53 for the hostname (see
  `var.mail_domain`, `var.route53_zone_id`).
- `terraform.tfvars` for the environment you are targeting, copied from
  `terraform.tfvars.example` and filled in.

## Validate without touching AWS

```sh
make tf-validate     # terraform validate, every environment (no backend, no credentials)
make tf-lint         # tflint, every module and environment
make tf-security      # checkov; every skip carries its reason inline
make tf-aws-on-floci  # full aws-dev apply, re-plan, destroy against a throwaway Floci
```

`tf-aws-on-floci` is the one that actually exercises `terraform apply`, a second `plan`
that must show zero adds or replacements, and `terraform destroy`, all against an
emulator, so plan-time bugs that `validate` alone would miss are caught before a real
account ever sees this configuration.

## Deploying for real (your account, your choice)

```sh
cd infra/terraform/envs/aws-dev
cp terraform.tfvars.example terraform.tfvars   # edit: region, domain, instance sizes
make aws-plan ENV=aws-dev                       # needs terraform.tfvars and AWS credentials
make aws-deploy ENV=aws-dev TAG=0.1.0           # registries, images, infra, migrations, rollout
```

`make aws-deploy` is one shot: it builds and pushes images to the ECR repositories the
Terraform created, applies the infrastructure, runs database migrations as a one-off ECS
task, then rolls out the services. Afterwards:

```sh
make aws-migrate ENV=aws-dev
make aws-admin ENV=aws-dev EMAIL=you@example.com ORG="My Company"   # PIISHIELD_ADMIN_PASSWORD in your env
```

Repeat against `aws-prod` with its own `terraform.tfvars` when ready. `aws-prod` has
deletion protection and multi-AZ by default; review `var.*` before applying.

## What AWS mode actually turns on in the app

`aws-dev` and `aws-prod` deliberately do NOT set `STORAGE=s3`, `AWS_SECRETS_ENABLED=true`
or `KEY_MODE=kms`: 0.1.0's app code has no read path for any of the three (`storage` and
`aws_secrets_enabled` are "accepted but unused" settings; `key_mode=kms` raises
`NotImplementedError`), so this release's environments do not set env values the app
cannot serve, even though the underlying AWS resources (the exports bucket, the KMS key)
are provisioned and real.

| Setting | `aws-dev`/`aws-prod` value | 0.1.0 behavior |
| --- | --- | --- |
| `KEY_MODE=local` | set | Real: `LOCAL_MASTER_KEY` comes from Secrets Manager (`module.secrets`), the only key backend 0.1.0 implements |
| `MAIL_BACKEND=ses` | set | Real: SES sending works once the domain identity is verified |
| `COOKIE_SECURE=true`, `CORS_ORIGINS=<hostname>` | set | Real: required by the production boot guard |
| `DATABASE_URL`, `REDIS_URL`, `SESSION_SECRET`, `API_KEY_PEPPER` | set | Real: delivered through the ECS task definition's Secrets Manager references (`module.secrets`) |

See [local-with-aws.md](local-with-aws.md) for the equivalent picture against the local
Floci emulator, and [security.md](../architecture/security.md) for the production boot
guard's full rules.
